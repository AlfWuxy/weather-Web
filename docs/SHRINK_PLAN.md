# 代码精简方案（功能零变化）

> 版本：v3（2026-09-26）· 状态：P0 到 P5 已完成，按阶段拆成 5 个依次叠放的 PR（第 4.1 节）· 基线：`main@60ef21f`
> 第一轮审核意见与处理见第 11 节，第二轮见第 12 节

本文面向审核者（人或 AI）。背景、硬约束、证据、每一步怎么做、怎么证明没改坏，以及需要产品负责人决定的事项，都写在这里。

---

## 1. 背景

- 项目：面向都昌县老年人高温风险的 Flask 网站，另有微信小程序入口。技术栈：Flask 2.3、SQLAlchemy、Jinja2、原生 JS，默认 SQLite。
- 规模（自有代码，不含 vendor）：Python 约 1.8 万行，模板 58 个约 1.4 万行，CSS 约 6000 行，JS 约 2700 行，路由 131 条。
- 目标：减少代码量和重复，降低长期维护成本。
- **硬约束：用户可感知的一切都不能变。**

## 2. "功能零变化"的精确定义

### 2.1 必须保持不变的内容

| 类别 | 内容 |
|---|---|
| 地址 | URL、HTTP 方法、endpoint 名（`url_for` 依赖它） |
| 输出 | 每个页面的 HTML、每个接口的 JSON、状态码、重定向目标 |
| 响应头 | 全部响应头（含 `Content-Type` 字符集、`Content-Disposition` 下载文件名、缓存头、安全头）；只忽略 `Date`、`Content-Length`、`Server` |
| Cookie 与会话 | Cookie 名称和属性（`HttpOnly`、`SameSite`、`Path` 等）；会话内容（登录身份、flash 提示、CSRF） |
| 权限 | 登录要求、角色校验、提示信息 |
| 限流 | 限流规则、各地址在同一请求序列下的放行与拦截、计数键名称与计数值 |
| 数据 | 每个操作之后的数据库状态，包括外键关系和有业务含义的时间字段 |
| 导出文件 | Excel 全部单元格的值、类型（数字、文本、日期）和显示格式；PDF 的页数和逐页文本；CSV 全文 |
| 前端 | 浏览器收到的 HTML、CSS、JS 逐字不变，因此渲染像素、交互结果、控制台输出也不变 |

### 2.2 各阶段允许的变化范围

| 阶段 | 允许变化的内容 | 其余一律不变 |
|---|---|---|
| P4 服务层 | 无。HTTP 层（2.1 全部各项）和数据库状态逐字一致 | 是 |
| P5 前端 | 无。渲染出的 HTML 与 `static/` 下的文件逐字不变；只允许模板源码层面的一种重组：逐字相同的片段移到 `templates/partials/`，原位置换成一行 `include`，由展开证明验证（5.2） | 是 |
| P6 离线脚本 | 本轮不改 | 是 |
| P7 文档 | 只改文档和生成脚本 | 是 |

确实需要改变输出的情况（例如修一个既有 bug），必须单独开 PR、打 `behavior-change` 标签，由产品负责人明确批准。

## 3. 安全网

### 3.1 行为锁（`scripts/behavior_lock.py`）

**录制方式**
- 固定种子数据（3 个村、4 类用户、480 条门诊、150 天天气、12 条预警、照护关系、避暑点等），时间冻结在 2026-07-20 10:00（北京时间），断开外网，固定 Python 哈希种子。
- 三种环境：`demo`（演示天气、默认功能开关）、`live`（带"在线"来源标记的夏季天气缓存、全部功能开关打开）、`winter`（冻结在 2026-01-15，寒冷天气缓存，种子日期整体平移）。
- 5 种身份（游客、普通用户、照护人、社区、管理员）访问：
  - 全部可枚举的 GET 路由；
  - 22 个带筛选参数的页面变体（6 个分析页的分层、分箱、滞后、日期倒置、非法输入，以及试点看板的天数参数）；
  - 14 个 JSON 写接口，以及 3 个报告导出表单。
- **请求之间完全隔离**：每个请求前，数据库恢复到种子状态，会话恢复到该身份刚登录后的 cookie。

**对比内容**：状态码、`Location`、全部响应头、Cookie 属性、解码后的会话内容、HTML/JSON 正文、数据库逐行变化、导出文件内容（Excel 单元格的值、类型和显示格式，PDF 页数与逐页文本）。规范化的只有：CSRF token、静态资源版本号、代码目录路径、每次随机生成的请求 ID。短码、令牌、游客 ID 用固定种子的随机序列生成，新旧代码逐字相同，不做抹除。

**判定**：缺失、变化、新增任何一个响应都算失败（第二轮审核后，新增也判失败）。预备登录会断言成功，避免"没登录上"导致两边都录成游客页面。

### 3.2 路由清单锁（`tests/test_route_manifest.py`）

131 条路由的（URL、方法、endpoint 名）存成清单，缺一条或多一条都会让测试失败。

### 3.3 限流锁（`scripts/ratelimit_lock.py`，已接入 CI）

行为锁录制时会关闭限流，这个脚本专门补上：把阈值调低，按固定顺序交替请求 12 组接口的兼容地址和 v1 地址，共 142 次；记录每次的状态码，以及限流存储里的全部计数键和值。当前结果：48 次被拦截，34 个计数键；连跑两次一致，`main` 与改后代码一致。断开外网，使用小时窗口，避免 CI 机器慢造成误报。破坏性测试：取消 `ml/predict-community` 的专属限流，抓到。

### 5.2 P5 模板去重（已完成，净减 223 行）

**原则：浏览器收到的每个字节都不变。** 只允许一种改动：把逐字相同的模板片段移到 `templates/partials/`，原位置换成一行 `include`。不把脚本和样式外提成静态文件，不改 `static/`，不合并"相似但不相同"的代码。

为什么这样定（回应第二轮 R2、R3）：外提脚本和样式必然改变 HTML（多出 `src` 属性或 `<link>` 标签），行为锁就得开例外；合并不同前缀的 CSS 会改变源码，甚至改变作用范围。改为模板源码层面的 `include` 之后，渲染出的 HTML 逐字不变，行为锁不需要任何例外，也用不到 `behavior-change` 标签。

**安全网：模板展开证明**（`scripts/template_expand_check.py`，已接入 CI）

- 把每个 `include` 按 Jinja 的规则原样展开（Jinja 会统一换行符，并去掉片段末尾的一个换行），展开结果必须与基线模板源码逐字相同。
- 这是静态证明，不依赖数据，覆盖模板里全部 `if`/`for` 分支，包括行为锁走不到的分支。
- 片段限制：扩展名 `.html`，自动转义与引用方一致；不含 `set`、`macro`、`block`、`extends`、`import`、`from`、`filter`、`with` 等改变作用域的标签；不含空白控制符；`include` 独占一行，从第 1 列开始；新片段必须被引用。
- 同一段代码在两页缩进不同时，用 `{% filter indent(N, first=True) %}` 还原缩进，展开时直接调用 Jinja 自己的 `indent` 函数。这种写法要求片段不含任何 Jinja 语法，因为 `indent` 作用在渲染结果上。
- 破坏性测试 8 项全部抓到：改片段一个字；片段加 `set`；缩进 4 改 8；`include` 改用双引号；`indent` 片段含 Jinja 表达式；片段加空白控制符；新增未被引用的片段；删掉一行 `include`。
- 行为锁照常运行，作为第二道保险：它实测了运行时的 `include` 与原位展开等价（2223 个检查点零差异），8 个片段都出现在录制到的响应里。

**原计划的像素锁和 Playwright 交互用例撤销。** HTML 和静态文件逐字相同，浏览器拿到的输入就完全相同，像素、交互、本地存储和控制台输出都不可能变化。这样也省掉了一整套容易误报的截图设施。

## 7. 执行纪律

1. **先锁后改**：每个阶段先补齐该阶段的安全网，在 `main` 上录好基线，并用破坏性测试证明新增的锁能抓到对应的变化，再动代码。
2. **一个 PR 一个主题**：P4、P5、P6 调查、P7 各自一个 PR，可以单独 `git revert`。
3. **每个提交都通过验证**：行为锁、场景锁（P4 起）、限流锁零差异；路由清单锁；全部测试（弃用警告视为错误）；手工契约测试；对整个分支相对 `main` 运行 `git diff --check`。
4. **三证据删除规则**，三条同时满足才删除：
   - 静态分析（vulture）判定无调用；
   - 全仓库搜索（代码、模板、JS、测试、脚本、文档、定时任务配置）无引用；
   - 行为锁和场景锁全量运行后的覆盖率显示从未执行。

   任何一条不满足就保留。动态调用（`getattr`、字符串拼接）要人工确认。**只适用于网站运行链路上的代码；离线脚本不适用**，原因见 5.3。
5. **遇到分叉就停**：看起来重复、实际有差别的代码，先证明等价；证明不了就不合并，列入决策清单。
6. **不顺手修 bug**：发现的问题记录下来，另开 PR。

## 附录 C：两个同名函数的等价性论证

**`_refresh_community_daily(community_code, status_date)`**
